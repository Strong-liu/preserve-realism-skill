> 策划存档：以下内容保留规划时的范围与阶段描述。第一版 `0.1.0` 已制作，用户已选择 MIT；当前交付和验证状态以仓库 README 及 `VALIDATION.md` 为准。

策划日期：2026-10-15  
阶段：需求已确认，策划完成后进入 skill 编写  
暂定 skill 名称：`preserve-realism`  
暂定 GitHub 仓库名称：`preserve-realism-skill`

## 1. 项目要做什么

制作一个可公开分享的通用 skill，帮助 AI 助手编写和改进写实图片、图片编辑及视频提示词，指导操作，并在获得结果素材后检查真实感与保真程度。

重点解决：真人脸被改成卡通脸、皮肤像塑料或蜡、纹理被磨掉、人物越修越不像本人，以及视频中人脸和材质随时间漂移。

项目将清晰度、自然纹理、人物身份和视频连续性分别处理。写出“高清”只表达期望；实际像素尺寸、可辨认的细节和人物是否保真，都需要单独核对。

预期使用体验：用户用自然语言描述需求，助手识别任务类型，生成可直接使用的提示词与操作建议；用户提供结果后，助手指出可观察的问题，并给出针对性的修改方案。

## 3. “通用”怎样实现

### 3.1 区分 skill 的使用环境与素材的生成工具

skill 由 AI 助手读取和执行；图片或视频则可以由另外的生成工具制作。两者无需绑定同一家公司或同一个模型。

采用开放的 Agent Skills 格式：一个 skill 文件夹至少包含 `SKILL.md`，文件开头使用 YAML 元数据，正文使用 Markdown 指令。这样可以减少对某个助手专有格式的依赖。[Agent Skills 格式规范](https://agentskills.io/specification)

Codex 与 Claude Code 都有读取 skill 的机制，但安装位置和调用方式由各自产品决定。发布时分别说明，兼容性需要实际验证。[Codex 官方说明](https://learn.chatgpt.com/docs/build-skills)、[Claude Code 官方说明](https://code.claude.com/docs/en/skills)

### 3.2 采用三层结构

| 层次 | 内容 | 通用方式 |
| --- | --- | --- |
| 通用核心 | 任务识别、真实感规则、保留项、编辑范围、结果检查 | 使用自然语言和标准 Markdown，独立于模型参数 |
| 能力适配 | 参考图、局部编辑、负面提示词、输出尺寸、视频输入 | 已知工具时核对其能力；未知时只给通用做法 |
| 使用入口 | 原生 skill 调用、手动提供指令、复制生成的提示词 | 根据使用环境选择，不要求生成工具直接安装 skill |

对于没有原生 skill 入口的聊天工具，可以尝试手动提供主指令及本次需要的参考内容。对于只接收生成提示词的工具，复制 skill 输出的提示词并附上必要参考图即可。此类方式属于手动使用，不能当作原生 skill 支持。

核心文件不依赖固定的工具名称、API、密钥、显卡或操作系统。特定平台的调用示例放在外围说明中。

这是项目采用的兼容设计。它不代表所有助手都支持自动发现 skill，也不代表不同模型会得到相同效果。

### 3.3 适配时的处理原则

- 未指定平台时，直接输出通用提示词，不强迫用户先选择模型。
- 用户要求平台参数或具体操作时，核对对应产品、版本和界面；无法核实时标明待确认。
- 只有确认支持独立负面提示词字段时，才输出该字段；其他情况把要求写入自然语言提示词。
- 参考强度、去噪强度、种子、尺寸等设置只在适用时讨论，不编造“通用最佳数值”。
- 看到工具支持某项功能，与验证该功能能保住人脸，是两件事；文档中分别记录。

## 4. 第一版功能范围

### 4.1 必须完成

1. **从零生成写实图片**：围绕主体、场景、构图、光线和材质编写提示词，降低卡通化和过度美化的倾向。
2. **编辑真人照片**：列清楚允许修改的部分和必须保留的部分，重点保留五官比例、身份特征及有依据的纹理。
3. **改写现有提示词**：识别与用户目标冲突的风格词、重复要求及模糊描述，保留用户原本想要的画面。
4. **指导生成或编辑**：说明参考图如何使用、哪些区域需要保护，以及何时先处理构图、再处理尺寸。
5. **检查图片结果**：根据实际看到的图片或局部对比，检查脸、皮肤、材质、光影和可观察的瑕疵。
6. **视频规则**：输出人物外观、动作、镜头运动与时间连续性的约束，并提供回看检查方法。
7. **修订建议**：根据发现的问题修改相关要求，保留已经有效的部分。

### 4.2 后续可扩展

- 有实际案例后，增加经过验证的平台适配说明。
- 出现重复文件处理需求后，再考虑尺寸检查、对比图或视频取帧脚本。
- 用户需要时，再增加 API 或生成工具自动调用。

第一版采用指令与参考文档实现。实际自动生成、付费调用、模型训练和自动修复流水线不作为本版验收条件。

## 5. 真实感与保真的核心规则

以下是待实现、待测试的工作规则。它们用于指导助手做决策，不能作为已经证明有效的宣传结论。

### 5.1 将“高清”拆成可检查的目标

| 目标 | 需要确认什么 | 检查方式 |
| --- | --- | --- |
| 像素尺寸 | 实际宽高、比例和交付需求 | 有原始文件或可靠元数据时核对；预览图不足以证明 |
| 可用清晰度 | 对焦主体、细节可辨程度、压缩或锐化痕迹 | 看整体和主体局部，不要求所有景深层面同样锐利 |
| 自然真实感 | 纹理、光线、材质和比例是否协调 | 按画面景别与使用目标检查 |
| 编辑保真 | 应保留的特征是否变化 | 对照原图、结果图及明确的保留项 |

“4K”“8K”等词不当作尺寸验证结果。对模糊或压缩严重的输入，不把模型新补出的细节称为原始细节的真实恢复。

### 5.2 纹理要符合画面条件

- 人脸细节按景别、光照、焦点及参考图处理；近景可以描述自然皮肤细节，远景不强求可见毛孔。
- 已有照片优先保留可见纹理；从零生成时描述自然变化，不默认增加痣、疤痕、皱纹或年龄。
- 头发、织物、金属、玻璃和木材按对应材料描述，不给所有表面套用同一组“细节”词。
- 不把颗粒、噪声、过度锐化、粗大毛孔或浓重 HDR 当作必须添加的真实感元素。
- 自然柔光、浅景深和合理修饰可按用户要求保留；检查它们是否损害了主体辨识度。

官方图像提示指南使用主体、构图、光线和纹理描述写实照片，局部编辑则分别说明修改目标与保留要求。本项目据此设计通用提示词结构，具体效果仍需测试。[OpenAI 图像提示指南](https://developers.openai.com/api/docs/guides/image-prompting)、[Google 图像生成指南](https://ai.google.dev/gemini-api/docs/image-generation)

### 5.3 保留人脸身份，允许任务需要的变化

真人编辑要区分稳定身份特征与可改变的状态。保留五官比例、脸部轮廓及参考图中可辨认的身份线索；表情、视角、姿态、光照是否改变，由用户任务决定。

换背景时允许环境光合理变化；改变表情时不要求原表情完全固定；视频中允许正常眨眼、说话、转头和透视变化。不能把“保留身份”写成“人物完全静止”。

多张参考图要标注用途，例如身份参考、衣服参考和场景参考，避免把所有图片中的人物或风格混在一起。

如果某个区域必须逐像素不变，应选择能明确保护原始区域的编辑或合成流程，并验证结果。仅靠提示词不能证明这一点。官方指南也提醒连续编辑可能改变应保留的细节。[OpenAI 编辑保留说明](https://developers.openai.com/api/docs/guides/image-prompting)

### 5.4 保留用户的画面意图

技能默认服务于写实任务。用户明确要求插画或卡通时，遵循其风格选择；要求“卡通背景中的真人脸”时，按区域表达风格。

“电影感”“时尚大片”“精致”等词可能有不同含义，应结合上下文改写成具体画面要求，不能一律删除。对冲突的要求，说明取舍或询问会影响结果的关键问题。

### 5.5 检查结论必须有素材依据

- 没有结果素材：交付提示词、操作建议和待执行的检查清单。
- 只收到文字描述：指出这是根据用户描述提出的修改建议。
- 看到图片：说明具体观察到的问题；看不清的局部标为无法判断。
- 只有低分辨率预览：可以判断明显的风格与结构问题，原始分辨率和细微纹理仍待核对。
- 只有视频截图：可以检查这些帧，不能据此确认整段视频没有闪烁或人物漂移。

## 6. 任务流程

### 6.1 共用入口

识别素材类型、任务目标、参考素材、允许修改项和交付要求。已有信息直接使用；只有缺失信息会改变处理方式时才询问。

识别后进入对应分支：从零生成、已有素材编辑、提示词改写，或结果检查。结果检查可以独立使用，不要求先执行生成流程。

### 6.2 从零生成图片

1. 保留主体、用途、构图和用户明确指定的风格。
2. 加入与画面相关的光线、材质和自然细节描述。
3. 检查写实要求与其他风格要求是否冲突。
4. 输出可复制的提示词，并将可选平台参数放在提示词之外。
5. 得到结果后检查真实感；没有参考身份时，不宣称人物“与本人一致”。

### 6.3 编辑已有真人照片

1. 能看到原图时先观察；只能看到描述时，说明判断依据。
2. 写出修改目标、修改区域和必须保留的特征。
3. 以原始照片为身份依据，按工具实际能力提出局部编辑或区域保护建议。
4. 明确可以随任务改变的表情、姿态或光照。
5. 对比原图与结果图，检查任务完成情况和身份、纹理是否受损。
6. 出现漂移时，优先回到原图或最近确认可用的版本，调整编辑范围；避免不断重绘已经失真的脸。

### 6.4 图片或视频结果检查

先说明收到哪些素材、能检查到什么范围，再列出有依据的问题与修改建议。图片可比较整体和局部；视频需检查动作过程及变化节点。

每轮修订优先处理最影响交付的问题，尽量保留已通过的部分。质量不再改善时，说明观察到的限制和可选方法，由用户决定是否继续。

### 6.5 视频生成与一致性指导

1. 使用文字设定或可用的参考素材定义人物外观与场景。
2. 将人物动作和镜头运动分别描述，避免互相矛盾。
3. 约束人脸、肤色、发型、服装与材质在动作过程中连续变化。
4. 保留眨眼、呼吸、表情和自然运动模糊；要求细节与运动协调。
5. 指导检查起止位置、转头、遮挡、快速运动和光线转换等容易暴露问题的片段。
6. 提供关键帧时按帧检查；具备连续视频查看能力并实际查看后，才报告时间连续性的检查结论。

## 7. 交付给 skill 使用者的内容

按任务需要交付，简短请求不强制生成完整报告。

| 内容 | 何时提供 |
| --- | --- |
| 可复制提示词 | 新生成、编辑或提示词改写 |
| 保留项与允许修改项 | 已有素材编辑、人物一致性任务 |
| 操作建议 | 用户需要参考图、局部保护或导出指导时 |
| 平台设置 | 工具和能力已明确，且设置影响本次任务时 |
| 质量检查结果 | 已取得并实际查看可检查的素材时 |
| 修订提示词 | 发现具体问题或用户反馈失败时 |

当前项目文档使用中文。skill 的解释默认跟随用户语言；第一版示例同时提供中文解释和英文提示词，不假设英文对所有工具都更有效。

## 8. 计划收录的示例

示例用于展示工作方式，后续测试后再决定哪些可作为公开效果案例。

### 示例 A：从零生成自然的人物照片

用户需求：“生成一个坐在咖啡馆窗边的人，像真实拍摄，不要塑料脸。”

示例提示词：

> A candid photograph of an adult sitting beside a café window, framed from the chest up. Soft window light falls across the face, with believable shadows and natural skin color variation. Facial detail should match this distance and lighting, with individual hair strands and gently textured clothing. Keep a relaxed expression and a photographic appearance without exaggerated facial proportions or a waxy skin finish.

检查重点：画面是否仍符合咖啡馆场景；皮肤是否自然；有没有因强调细节而产生突兀颗粒或过度锐化。

### 示例 B：真人换背景，保留面貌

用户需求：“把这张照片的背景换成街道，人要保持本人，皮肤不要磨平。”

示例提示词：

> Replace the background of the supplied portrait with a believable outdoor street. Use the original photograph as the identity reference. Retain the person's facial proportions, skin detail visible in the source, hairstyle, expression, and pose. Make any necessary lighting adjustment subtle and consistent with the new surroundings. Keep the face photographic, without beautification that changes their appearance or invented facial marks.

操作重点：若工具支持区域保护，保护人物主体；是否需要合成或局部修改，取决于用户的保真要求和工具能力。

检查重点：对比五官、脸型和原图可辨认的纹理；同时检查人物与新背景的光影衔接。

### 示例 C：人物转头的视频

用户需求：“让参考图中的人物慢慢转头，保持真实，不要过程中换脸。”

示例提示词：

> Animate the person in the supplied reference image making a slow, comfortable head turn, with the camera staying in place. Keep their recognizable facial structure, hairstyle, clothing, and photographic appearance consistent as the viewing angle changes. Allow natural blinking and subtle expression movement. Skin and fabric detail should move coherently with the subject, with plausible motion blur and continuous lighting throughout the shot.

检查重点：转头前后是否仍能认作同一人物；纹理是否贴合动作；遮挡处是否出现突然换脸、色彩跳变或材质变化。

## 9. 拟定仓库结构

以下是下一阶段的文件设计，本阶段不创建这些文件。

```text
preserve-realism-skill/
├── README.md
├── LICENSE
├── docs/
│   └── PROJECT_PLAN.md
└── skills/
    └── preserve-realism/
        ├── SKILL.md
        └── references/
            ├── image-workflows.md
            ├── video-consistency.md
            └── examples-and-review.md
```

- `README.md`：项目定位、实际兼容情况、安装与调用方式、手动使用方式、例子和能力边界。它服务于 GitHub 读者，放在仓库根目录。
- `LICENSE`：发布前选择许可证，明确他人使用和修改仓库内容的条件。
- `docs/PROJECT_PLAN.md`：保存项目策划，方便后续核对范围。
- `SKILL.md`：包含名称、触发描述、共用规则、任务分支和参考文件入口，保持简洁。
- 图片参考文件：详细的生成与编辑方法、纹理尺度、清晰度及身份保留规则。
- 视频参考文件：动作与镜头描述、人物连续性和视频检查范围。
- 示例与检查参考文件：输入输出示例、常见问题及有素材依据的检查方式。

按照任务只读取相应参考文件，减少不必要的上下文。第一版不预建没有用途的脚本或素材目录。若需要 Codex 界面显示信息，可后续添加可选的 `agents/openai.yaml`，核心工作流不依赖它。

## 10. 怎样验证它有用

### 10.1 文件与行为验证

检查 `SKILL.md` 元数据、名称、目录名、引用路径和未完成模板内容。再使用真实请求检查它是否触发恰当、输出完整、保留用户意图。

格式校验通过，只代表格式符合要求；还需要下面的行为与素材检查。

| 测试请求 | 预期行为 |
| --- | --- |
| “写一个自然的真人摄影提示词”，未指定平台 | 直接给通用提示词，不编造参数 |
| 真人照片换衣服，要求保留脸 | 区分衣服修改与身份保留，并说明参考图用途 |
| 换表情，要求仍是同一人物 | 允许表情变化，保留稳定身份线索 |
| “要更清晰”，附上低清照片 | 区分输出尺寸、可见细节与模型补出的细节 |
| 远景人物照片 | 不强求远景毛孔，不把细节写成近景特写 |
| 请求检查结果，却没有提供结果图 | 提供待执行清单，不声称已检查 |
| 只有三张视频截图 | 说明帧级观察范围，不宣称整段无闪烁 |
| 用户明确要求卡通人物 | 尊重风格，不强行转成真人摄影 |
| 用户指定某平台专有参数 | 依据该工具能力输出或标为待确认 |

### 10.2 素材效果验证

选择代表场景，比较原始提示词与经 skill 改写的提示词。尽可能保持模型版本、参考图、比例和可控制的设置一致；支持固定种子时可以使用，但不要假设种子跨模型有效。

每个场景比较多个结果，记录实际使用的提示词、设置和原始输出，避免以单张最佳结果说明普遍改善。公开示例说明选择方式，不把修图后的展示图当作未经处理的原始输出。

图片记录：任务是否完成、是否写实、纹理是否自然、光影是否协调、有参考图时身份是否保留，以及是否引入新瑕疵。视频另记录时间连续性与检查覆盖范围。

优先给出问题位置和可观察证据；使用等级评价时先定义标准。不把主观评分当作身份认证或客观相似度指标。

### 10.3 兼容性记录

区分“符合开放格式”“文档说明有支持”“已在某版本实际试用”。只将实际试用的环境标为已测试。即梦、可灵等生成工具可作为提示词使用对象；是否具备原生 skill 功能另行核对。

## 11. 制作与发布路线

| 阶段 | 主要工作 | 交付与完成条件 |
| --- | --- | --- |
| A：项目策划 | 固定目标、通用方式、规则和验证方法 | 本 MD 可供评阅，范围清楚 |
| B：编写 skill | 创建 `SKILL.md` 和实际需要的参考文件 | 工作流完整，引用可用，格式校验通过 |
| C：试用改进 | 测试生成、真人编辑、缺少素材和视频场景 | 行为符合范围；效果声明有相应记录 |
| D：整理发布包 | 编写 README、选择许可证、整理可公开示例 | 他人能理解用途、安装和使用方法 |
| E：GitHub 发布教学 | 演示创建仓库、上传文件、检查目录和分享入口 | 用户自己的仓库可以被访问和按说明使用 |

发布教学优先提供浏览器上传方式，按需要补充 Git 命令行方式。发布阶段再核对 GitHub 当前操作文档，使用用户实际选择的账号和仓库名称。

发布到 GitHub 后，用户可以获取 skill 文件夹，按各助手的方式安装，或按 README 手动使用提示词工作流。若未来需要插件目录或市场分发，再单独制作对应打包配置。

## 12. 后续阶段再决定的事项

以下事项不阻碍编写通用核心，也不需要现在选定：

- 最终项目名、skill 名和 GitHub 仓库名；当前名称用于策划。
- README 使用中文，还是增加英文版本；本计划先以中文为主。
- GitHub 用户名与仓库公开设置；发布阶段由用户选择。
- 开源许可证；准备发布包时解释常见选择，再确定。
- 首批实际测试工具；按届时可使用的环境选择，不改变通用定位。
- 可公开的示例素材；仓库仅收录适合公开分享、来源清楚的素材，测试用的私人原图与配置留在本地。
